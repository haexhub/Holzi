## A. Phase 10 — production deploy

The single biggest remaining MVP slice. Several pieces don't need a deployment target; one needs a real VPS.

### A.1 Infra-as-code (can do without a VPS)

- [ ] **Frontend → backend hand-off.** Decide how the Nuxt `dist/` reaches the hermes container. Options:
  - Bake the built frontend into the hermes-server image (`COPY --from=frontend-build /dist /opt/hermes/frontend/dist`)
  - Build it in a sibling compose service whose volume is mounted into `hermes-server`
  - Ship as a separate static-only image behind Traefik with a path prefix
  *Recommendation*: multi-stage Dockerfile in this repo that pulls + builds holzi-frontend's `main`. Keeps the deploy a single `docker compose up`.
- [ ] **Compose `--profile traefik`** path. Already roughed in via the `traefik` service block — verify ACME against a throwaway domain or use the staging CA.
- [ ] **Service-discovery labels** for the external-Traefik path. `traefik.enable=true` etc. are present; sanity-check the `traefik.docker.network` reference resolves when both Traefik and hermes are on the same `proxy` network.
- [ ] **Rate-limit middleware** in Traefik labels: 10 req/min/IP on `/v1/*` and `/api/chat` for failed-auth (per design doc §2.5).

### A.2 Backup / ops (needs a target before it's testable end-to-end)

- [ ] **Systemd timer** for daily SQLite backup. Script that calls `sqlite3 hermes.db .backup …` + ships to S3 / B2 / local rsync. Service unit + timer unit + install script.
- [ ] **fail2ban** jail config that watches `hermes-server.log` for `auth_rejected` and bans on N retries. Out of MVP scope per design doc §2.5 but worth scripting now.
- [ ] **Log rotation / structured-log forwarding** — currently structlog JSON to stdout. Decide: Docker default driver + log-rotate, or push to a log aggregator.

### A.3 First deploy

- [ ] Pick a VPS (Hetzner / Netcup). Document the bootstrap sequence in `docs/deploy.md`.
- [ ] One-time interactive `claude login` inside the haex-claude-proxy container.
- [ ] One-time interactive Signal device linking against `signal-cli-rest-api`.
- [ ] DNS + Let's Encrypt verification.

## B. Frontend polish

All of these compile against the existing `/api/*` surface — no backend changes needed.

- [ ] **Token-by-token "typing" animation.** Backend already streams incremental `text` SSE events; `useChatStream` concatenates them. Just thread `onText` callback into a reactive ref the chat view watches so partial text renders as it arrives.
- [ ] **Dark-mode toggle.** CSS variables for both themes already in `tailwind.css`; need a `useColorMode`-style composable + a toggle in the header.
- [ ] **Conversation auto-title** from the first user message. Currently shows `"web #1"`. Trivial: when a new conversation is created, take the first 40 chars of the message and `PUT /api/conversations/{id}` — except that endpoint doesn't exist yet. Alternative: have backend auto-derive on conversation create (server-side).
- [ ] **Error UX**: reconnect-on-drop for SSE, surface upstream LLM errors more legibly than the current "Chat-Fehler" toast.
- [ ] **Mobile responsiveness**. Three-column layout collapses on phones (it doesn't currently — `grid-cols-[260px_1fr_320px]` is a fixed pixel layout).
- [ ] **Empty-state UX** for first-time users: explain the token field, link to a place to generate one.

## C. Backend polish

- [ ] **Connection-pool sanity check** post-SQLA refactor. Default `AsyncAdaptedQueuePool` size is 5. For our usage (Signal worker + scheduler + occasional HTTP) it should be enough; verify under a synthetic load.
- [ ] **`engine` rename** of the test fixture (currently `conn`, but yields an `AsyncEngine` since #11). Pure clarity; would touch ~15 test files.
- [ ] **Conversation auto-title** server-side — see B above. Could be a one-liner in `/api/chat` when `payload.conversation_id is None`: derive title from the first message.
- [ ] **Cleanup**: confirm `aiosqlite` is still needed as a top-level dep (it's pulled in transitively by `sqlalchemy[asyncio]`; the top-level entry may be redundant).
- [ ] **Better `/api/chat` error semantics**: distinguish "upstream LLM unreachable" (502/504) from "agent error" (current 500) — today every agent exception emits an `error` SSE event with a 200 envelope.

## Open architectural questions

1. **`/api/chat` partial state on error.** If the agent fails mid-tool-loop, the user message is persisted but no assistant turn. Acceptable for now; revisit if it confuses users.
2. **Conversation 6h gap heuristic for Signal** (Phase 4 design choice). Has it held up? Worth measuring once we have actual usage data.
3. **Backend response shapes vs. SQLAlchemy row objects.** Currently the routes build dicts manually then pass them to FastAPI for `response_model` validation. Could just use SQLAlchemy `Row._asdict()` or Pydantic `model_validate` — small cleanup if/when it bothers anyone.
4. **MCP client config format.** JSON in env var feels brittle; a `hermes.toml` or `.yaml` might age better. Decide when the client manager actually lands.
